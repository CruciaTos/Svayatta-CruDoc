# Find-a-person fix plan (Teams, Consults/Referrals, Files)

Diagnosed 2026-10-28 by workflow wf_288c21d2-e90. Nothing implemented yet.

## Teams / clinic invites by CruDoc ID (Settings → Team → Add person → "CruDoc ID" segment; the invitee sees it as a pop-up, in Settings → Clinic invites, and on the onboarding Join screen)

**How the recipient is found:** The admin picks "Invite by: CruDoc ID" (invite_sheet.dart:286-306) and types the ID. The field uses textCapitalization.characters, and the client check is looksLikeCrudocId (referral_network.dart:202-207), which works the same way as the server's normalizeCrudocId (crudoc-id.ts:37-43). Case, dashes and spaces don't matter, a "CD" prefix is fine, and O is read as 0 and I/L as 1. So typing or pasting "k7q92xmb", "K7Q9-2XMB" or "k7q9 2xmb" all resolve. The raw trimmed text goes out as payload key 'crudocId' (invite_sheet.dart:116 → clinic_team_api.dart:178). The server (clinic.ts:927-955) then:
1. Normalizes the ID.
2. Looks it up with uidForCrudocId (crudoc_ids/{id}, crudoc-id.ts:80-84).
3. Requires users/{uid}.discoverable != false (isDiscoverable, clinic.ts:406-409, 938), plus admin.auth().getUser.
4. Refuses your own ID.
5. Turns the ID into Firebase Auth phoneNumber, or the email if it is verified, or fails with failed-precondition.
From that point it is an ordinary phone or email invite. The CruDoc ID is not stored on the invite. Delivery is by phone/email match: the inbox copy is written only when uidForPhone(phone) finds someone (clinic.ts:1078-1082), and accepting needs the token's phone or verified email to match (clinic.ts:796-829). The phone and email picks are still separate: phone typed, or chosen from contacts via matchContacts (contact_invite_picker.dart:34-77, clinic.ts:1732+). Where a user sees their own ID: Settings → Profile → "Your CruDoc ID" card with Copy (desktop_settings_screen.dart:606, 645-680; myCrudocIdProvider at referral_network.dart:528-532 → referralNetwork myCrudocId → ensureCrudocId at referrals.ts:670-673). The phone has it too: mobile Settings opens the same DesktopSettingsScreen per section (mobile_more.dart:61-71, 535-546; the profile section is always listed, desktop_settings_screen.dart:94-116, 150). The ID is not shown on the Join-a-clinic screen or in Settings → Clinic invites.

### CruDoc ID gaps
1. ID invites aren't addressed to the uid. The server turns the ID into a phone or email and drops the uid (clinic.ts:937-954). Delivery (inbox write, clinic.ts:1078-1082) and acceptance (clinic.ts:821-829) only work through phone/email matching. Needed: store inviteeUid (and a formatted crudocId) on the invite, always write the inbox for that uid, and accept on `inviteeUid === uid`. That makes Google, email-only and unverified accounts work.
2. No preview step: the sheet never calls findByCrudocId to show who the ID is before sending.
3. No owner check: a target who runs their own clinic is invited and then can't join.
4. The findable rule is wrong. The phone-number switch hides the ID too, with a misleading 'no one has that ID'.
5. Privacy: the resolved phone number is stored on the invite and shown to admins.
6. Two lookup paths: clinicTeam (no rate limit) and referralNetwork (rate limited, plus a doctor check). One shared server helper and one shared Dart field/lookup are needed.
7. Invitees can't see their own ID on the Join screen or in Settings → Clinic invites, only in Settings → Profile (present on phone and desktop).
Already fine: payload key names, callable name and region (asia-south1), rules, and the collection-group indexes. Typing or pasting the ID with or without the dash, in lower case, with spaces or a CD prefix, with O/I/L, all resolve correctly on both sides.

## Files sending to a colleague: Send sheet, desktop colleague strip (drag or compose), and Explorer drop onto an avatar. Covers the Wi-Fi (LAN) and cloud paths and accept/download on the receiver's side, including the uncommitted working-tree changes.

**How the recipient is found:** A recipient can only come from the sender's current clinic member list. No search field exists, and nothing takes a phone number, email or CruDoc ID.
- Source: clinicMembersProvider streams clinics/{clinicId}/members, with clinicId taken from clinicAccessProvider (lib/features/team/data/team_providers.dart:15-28).
- Send sheet: filters to `m.uid != myUid && m.active` (lib/features/files/presentation/send_sheet.dart:28-29).
- Desktop strip: stripColleaguesProvider applies the same filter and sorts by who you sent to last (widgets/colleague_strip.dart:21-43). The strip shows only when `!cruIsPhone && hasColleaguesProvider` (files_screen.dart:406-409). On a phone the only entry point is the sheet, opened from FilesActions.sendToColleague (files_actions.dart:489-496).
- Eligibility check: colleagueBlockReason (lib/features/files/data/colleague_send.dart:14-31) needs active, clinical.view, clinical.edit, and an assignment check when the clinic is scoped. It reads the member doc's stored perms.
- Server check: the file_offers create rule requires `isClinicMember(clinicId, request.resource.data.to)` (firestore.rules:819). isClinicMember (firestore.rules:52-57) means either the owner uid or an active members/{uid} doc.
- Solo doctor: the sheet only shows "No colleagues in your clinic to send to." (send_sheet.dart:31-38). hasColleaguesProvider (transfers_sheet.dart:42-50) also hides the Transfers button and the strip (files_screen.dart:401-409).
- Result: sending to anyone outside the clinic, by CruDoc ID or any other way, is impossible today.

### CruDoc ID gaps
Files sending has no CruDoc ID support at any layer.
1. UI: there is no field to type or paste an ID in send_sheet.dart, compose_transfer_dialog.dart or colleague_strip.dart. Typing and pasting would already work if one were added: looksLikeCrudocId (lib/features/dental/referrals/referral_network.dart:202-207) and server normalizeCrudocId (functions/src/crudoc-id.ts:37-43) both accept lower case, with or without the dash, spaces, a CD prefix, and O for 0 or I/L for 1.
2. Lookup: ReferralNetworkApi.findByCrudocId (referral_network.dart:319-322) → referralNetwork action 'findByCrudocId' (functions/src/referrals.ts:680-711). It returns uid, name and isDoctor, is limited to 60 lookups per hour, and returns not-found when discoverable is false. It is never called from Files.
3. Offer location: offers live under clinics/{senderClinic}/file_offers, and the rules require isClinicMember(to) (firestore.rules:819). Sending outside the clinic needs a location written by the server (top-level, or users/{to}/file_inbox) through a callable that checks the recipient. The recipient also needs a new listener, because watchIncomingOffers reads only their own clinic (file_offers_repository.dart:95-115).
4. Bytes: the shared copy sits in clinic-blobs/{senderClinic} and only that clinic's clinical.view can read it (storage.rules:200). createReceivedFile looks only in the recipient's clinic (files_repository.dart:600-611). The server needs to copy the object into clinic-blobs/{recipientClinic}/{sha}/original, where onBlobFinalized marks it ready, or hand out short-lived signed URLs like referral attachmentUrl (referrals.ts:637-668).
5. Patient: patientId refers to the sender clinic's patient and means nothing to the recipient. Arrive as unassigned (kUnassignedPatientPrefix in file_models.dart) and let the recipient pick the patient with Change patient.
6. Wi-Fi: not possible across clinics. The device registry is per clinic (clinics/{id}/devices), and LanServer accepts only devices in its own clinic registry (lan_server.dart:188-198). Cross-clinic sends would be cloud only.
7. Policy: decide whether non-doctors can receive (findByCrudocId returns staff with isDoctor=false; referrals require doctors). Record patient consent, as referral send does with consent:true (referrals.ts:440-443).
8. Possible merge: referral_shares already shares files between doctors by uid. It covers attachments under referral_uploads/<uid>/<shareId> (send at referrals.ts:440-560, MAX_ATTACHMENTS 10, 15 MB), pushTo, spend rate limits, and attachmentUrl. A 'files only' share, or a new referralNetwork 'sendFiles' action, could serve both Files (outside the clinic) and Consults. In-clinic sends would keep using file_offers.

## Consults / Referrals (dental Referrals screen, 'referralNetwork' callable), including CruDoc ID lookup and referral file attachments

**How the recipient is found:** The recipient is always a saved referral contact with a non-empty crudocUid (ReferralContact.onCruDoc, referral_models.dart:112-116). New referral only offers a dropdown of saved contacts (referral_dialogs.dart:373-417), and send uses contact.crudocUid (referral_share_flows.dart:102). A contact gets crudocUid in three ways:
(1) A phone or verified-email match. EditContactDialog._save calls matchContacts (referral_dialogs.dart:655-669), and opening ContactDirectoryDialog runs refreshContactMatches (referral_dialogs.dart:809-815, referral_share_flows.dart:923-969). ## Deploy

Functions only, no new callable, so no manual IAM step: `firebase deploy --only functions:referralNetwork,functions:clinicTeam,functions:onFileOfferCreated --project svayatta-crudoc-dev`, with the same --no-invoker-iam-check handling used on 2026-10-27 so the dev callables stay reachable. Deploying clinicTeam also ships its not-yet-deployed remove-member change. The YOUPI secret placeholder may block a deploy that isn't scoped with --only. No firestore.rules, storage.rules or index changes are required (server writes bypass rules, and the new invite queries are equality-only and collection-scoped). The rules need a deploy only if file.send/file.receive are added to the access_logs create rule (firestore.rules:519, optional). Then rebuild the apps (phone via adb, Windows with --dart-define-from-file=google_desktop_oauth.json) and test with two accounts: an invite by ID to a Google-only account, a referral by ID, and files by ID across two clinics.
